# МАЙТИМ — технические требования к MVP

Версия: 1.0  
Дата: 24 октября 2026 года

Продуктовые сценарии: [mvp.md](../product/mvp.md). Палитра: [colors(1).txt](../product/colors%281%29.txt).

## 1. Принципы и инфраструктура

МАЙТИМ — адаптивный веб-сервис. Язык, фреймворки, устройство фронтенда и бэкенда выбирает Codex. Приоритеты: простота сопровождения, сохранность пользовательских данных, быстрое добавление активностей и устойчивый недельный цикл.

- Бэкенд размещается на Render.
- База данных и файловое хранилище — Supabase.
- По предоставленному владельцем контексту у Codex есть Render API Key и Supabase API Key для настройки ресурсов и деплоя. Наличие и права проверяются при реализации; данный документ не подтверждает фактический доступ.
- Токен Telegram-бота и серверный секрет Supabase уже предусмотрены в environment Render. Существующие имена переменных и инфраструктуру необходимо сначала изучить, затем переиспользовать.
- Секреты доступны только серверу; не попадают в клиентскую сборку, репозиторий, сообщения или логи.
- В репозитории документируются имена переменных, запуск, миграции, деплой, восстановление и ручные операции без секретных значений.
- Для MVP достаточно модульного приложения без обязательных микросервисов. Выбранная конфигурация хостинга должна поддерживать фоновое расписание независимо от посещений сайта.

## 2. Каркас и новые активности

Общие модули:
- идентификация пользователей, профиль и Telegram-контакты;
- недельные раунды, добровольная запись и история участия;
- подготовка, проверка и публикация мероприятий;
- очередь уведомлений;
- обратная связь и ачивки;
- фоновые задания, аналитические события и эксплуатационный контроль.

Активность определяет правила формирования группы, собственные данные, инструкции, представление и условия достижений; общая форма результата использует «Да/Нет», оценку 1–5 при «Да» и причину при «Нет». Random Coffee — первая реализация.

Новый формат использует существующие профили, историю, расписание и доставку. Не нужно заранее создавать универсальный конструктор всех возможных мероприятий. Общие сущности отделяются от специфичных полей формата; изменения правил не переопределяют смысл старой истории.

Названия команд сопоставляются автоматически по требованиям продукта без ручного справочника. Алгоритм выбирает Codex; LLM не обязательна. Исходное название и вычисленный результат сохраняются отдельно, неопределённость не препятствует участию.

## 3. Данные и миграции

- Постоянный внутренний ID пользователя связан с Telegram ID; username не является ключом идентификации.
- Постоянные идентификаторы связывают раунды, группы, участие, ответы и достижения.
- История сохраняет контекст встречи: состав, команду и город на момент подбора, формат и необходимые версии правил.
- Все изменения структуры БД, начальная схема и преобразования данных оформляются версионируемыми миграциями в репозитории.
- Новые поля и изменения формата предусматривают обработку существующих записей.
- Обычный деплой не удаляет и не обнуляет профили, историю, ответы или ачивки. Повторное применение рабочих операций не создаёт дубликаты.
- Переход между версиями приложения и БД проектируется совместимым; откат кода не требует удаления пользовательских данных.
- Перед потенциально разрушительными миграциями создаётся резервная копия или проверенная точка восстановления. Документируется восстановление, включая файлы Storage, если они затрагиваются.
- Значимые миграции проверяются на данных предыдущей схемы.
- Аналитические события хранятся в отдельной таблице с историей изменений и уникальным ключом события. Она дополняет рабочие таблицы, а не заменяет их.

## 4. Расписание и состояния

Часовой пояс бизнеса — Europe/Moscow. В БД моменты времени хранятся однозначно; преобразования не зависят от часового пояса сервера.

| Время, МСК | Действие |
| --- | --- |
| Вторник 21:00 | Закрыть запись, подготовить следующий раунд и отправить владельцу состав и результат проверки |
| Среда 09:00 | Завершить предыдущий период встреч, опубликовать подготовленный раунд и отправить инструкции; открыть запись на следующий |
| Вторник 09:00 | Единственный запрос обратной связи по текущему раунду, только при отсутствии окончательного ответа |
| Четверг 09:00 | Пригласить ещё не записавшихся пользователей с подключённым ботом на следующую неделю |

Запрос ОС один, во вторник утром; дополнительных напоминаний нет. Текущее окончание периода встреч в среду сохраняется.

GitHub Actions запускает четыре события в неделю, cron задан в UTC (МСК−3): вторник 06:00/18:00, среда 06:00, четверг 06:00. Запуск может задерживаться платформой. Пропущенные этапы догоняются по сохранённым срокам в пределах допустимых окон; повторы доставки обрабатываются в течение того же запуска.

Состояния записи, черновика, публикации, завершения, обратной связи и доставки сохраняются в БД. События разных раундов, совпадающие по времени, обрабатываются независимо и явно привязаны к своим датам.

## 5. Устойчивый планировщик

Codex выбирает cron или другой устойчивый механизм. Единственный таймер в памяти веб-процесса недопустим.

Обязательные свойства:
- выполнение без открытого сайта и действий владельца;
- защита от одновременного выполнения одного этапа;
- идемпотентность: повтор не создаёт новые встречи, раунды, ачивки или события;
- сохранение прогресса и восстановление после остановки;
- обнаружение пропущенных запусков и контролируемое выполнение просроченных этапов;
- проверка актуального состояния перед действием, чтобы после долгого простоя не отправлять устаревшие приглашения и напоминания;
- недопустимость публикации непроверенного или повреждённого состава;
- возможность безопасно повторить незавершённый этап документированной серверной операцией.

Для случаев 0, 1, 2 участников, нечётного количества, повторных встреч и неопределённой команды реализуются правила продуктового описания.

## 6. Предварительный контроль и получатель

Владелец и получатель служебных сообщений: **@artemiy_mikhaylov**.

До запуска владелец активирует бота. В рамках настройки необходимо получить и проверить его числовые Telegram user ID и chat ID и сохранить в защищённой серверной конфигурации. Username используется как ориентир для привязки, но не как постоянный идентификатор доставки или основание служебных прав. Нельзя автоматически назначать владельцем любого пользователя с введённым таким именем.

Во вторник 21:00:
1. Сохраняется черновик с составом встреч.
2. Проверяются полнота и корректность распределения.
3. Владельцу отправляются даты, состав, число участников, предупреждения, ошибки и время публикации.

Одобрение ответом не требуется. Отсутствие ответа владельца означает продолжение по плану, если данные корректны и раунд не приостановлен.

До публикации владелец может исправить данные через БД. Система не перезаписывает исправления, проверяет итоговый состав и публикует именно сохранённый черновик. Нужно поле приостановки публикации конкретного раунда и инструкция его использования.

После запуска отправляется один итоговый отчёт о публикации и доставке. Некорректный состав, явная пауза или техническая ошибка не обходятся молчанием владельца. Сбой системы нельзя выдавать участнику за нехватку собеседников.

## 7. Telegram-доставка

- Уведомления сохраняются в устойчивой очереди в БД до отправки.
- Для сообщения фиксируются тип, получатель, раунд, статус, попытки, последняя ошибка и время следующей попытки.
- Временные ошибки обрабатываются повторно с задержками; постоянные, включая запрет сообщений ботом, фиксируются отдельно.
- Сбой одному получателю не блокирует остальных.
- Уже подтверждённые успешные отправки не повторяются намеренно.
- Учитывается неопределённый исход: API мог принять сообщение до потери ответа. Абсолютная гарантия отсутствия дублей в этом случае не заявляется.
- Перед запросом обратной связи проверяется актуальный ответ; окончательно ответившему запрос не отправляется.
- Лимиты провайдера учитываются механизмом очереди.
- Карточка встречи доступна в веб-сервисе независимо от успеха уведомления.

## 8. Критические уведомления без спама

В Telegram владельца приходят только предусмотренные отчёты расписания и важные эксплуатационные инциденты, требующие внимания.

Критические случаи:
- БД или Storage недоступны, операции чтения/записи существенно нарушены;
- исчерпан лимит объёма БД, Storage или другой ресурс, из-за чего перестают выполняться необходимые операции;
- приближение к лимиту требует скорого вмешательства и подтверждено доступными метриками;
- пропущена или провалилась подготовка/публикация раунда;
- обнаружен некорректный состав или состояние данных, блокирующее запуск;
- массовая или длительная невозможность Telegram-доставки;
- миграция или деплой оставили сервис неработоспособным.

Требования к контролю:
- использовать доступные метрики и API Render/Supabase; не предполагать, что любая квота доступна программно;
- если измерение ресурса недоступно, документировать ограничение и контролировать реальные ошибки операций;
- определить пороги и допустимые задержки в конфигурации и эксплуатационной документации;
- проверять ожидаемые запуски по срокам и сохранённому результату отдельным контролем, который не зависит только от успешного выполнения самого задания;
- учесть общий отказ: проверка пропущенного cron должна иметь независимый триггер относительно проверяемого задания; один упавший процесс не может быть единственным источником собственного алерта;
- одна проблема создаёт один открытый инцидент; однотипные ошибки агрегируются;
- повторные сообщения подавляются на настраиваемый период; повтор допустим при ухудшении или длительном отсутствии восстановления;
- после восстановления — одно сообщение о закрытии инцидента;
- обычные успешные операции, каждый повтор отправки, единичная ошибка пользователя и отдельный заблокированный бот не создают критический спам.

Сообщение содержит: что сломалось, что затронуто, время и раунд при наличии, краткую причину, полезное действие или ссылку на диагностику. Без секретов и лишних персональных данных.

Если Telegram недоступен, инцидент сохраняется и отправляется после восстановления. Если основной сервис или БД полностью недоступны, внешний контроль должен сохранять собственное состояние доставки. Выбранный способ и его пределы документируются.

## 9. UI и поведение загрузок

- Минималистичный, ненавязчивый и аккуратный дизайн без избыточных украшений и анимаций.
- Визуальные цвета и состояния берутся из [исходной палитры](../product/colors%281%29.txt), сохраняются семантические назначения и прозрачность.
- Адаптация к мобильному и десктопному браузеру: читаемые размеры текста, удобные зоны нажатия, корректные переносы, отсутствие горизонтального скролла основных экранов.
- Основные экраны: онбординг, профиль и ачивки, текущая активность, запись на следующую, обратная связь.
- Фоновые загрузки и обновления не перекрывают уже доступный контент.
- Зависимые данные загружаются заранее, когда это уместно; индикатор показывается только там и тогда, где пользователь ожидает ещё не загруженные данные.
- Первая загрузка раздела может использовать локальный скелетон или компактный индикатор. Не показывать полноэкранный лоадер при каждом переходе или фоновом запросе.
- Действия записи, отмены и отправки ответа имеют понятное состояние выполнения и защиту от повторного нажатия. Успех не показывается до подтверждённого сохранения, если не реализован корректный откат оптимистичного действия.
- Различаются пустое состояние, ошибка и загрузка. Сбой обновления не стирает уже показанные данные.
- Формы сохраняют введённое при временных ошибках и дают повторить действие.
- Доступны клавиатурный фокус, подписи полей, читаемый контраст и корректные сообщения об ошибках.
- Поддержка тёмной темы не становится обязательной только потому, что она есть в файле палитры.

## 10. Пользовательские тексты и техническая информация

В пользовательском интерфейсе нет тестовых данных, debug-панелей, stack trace, SQL, внутренних ID, конфигурации инфраструктуры, секретов и сырых ошибок API. Тестовые режимы и данные изолированы от рабочей среды.

Ошибки объясняются простым языком с полезным следующим действием. Диагностика остаётся в защищённых логах и служебных сообщениях.

Допустима небольшая ненавязчивая подпись, например:
> Небольшой эксперимент для нашей команды. Иногда что-то может работать неидеально — если заметишь проблему, дай знать.

Она не закрывает основной сценарий и не заменяет обработку ошибок. Не нужно показывать технические подробности устройства сервиса.

## 11. Доступ и безопасность данных

- Telegram-данные проверяются на сервере; клиентские поля не считаются доказательством личности.
- Пользовательский API возвращает только собственные данные и разрешённые данные собеседников.
- Чужие ответы, комментарии, очередь уведомлений, служебные отчёты и аналитическая таблица недоступны обычному участнику.
- Серверный ключ Supabase не отменяет проверки прав в API.
- Фоновые и служебные операции защищены от публичного произвольного запуска.
- Секреты и содержание персональной переписки не логируются.
- Вход коллег не ограничивается корпоративной проверкой или кодами, согласно продуктовым требованиям.

## 12. Проверки перед запуском и эксплуатация

Без ожидания реальных недель нужен сценарный прогон часов и этапов:
- два последовательных раунда, закрытие записи и открытие следующей;
- подготовка вторник 21:00, публикация среда 09:00;
- единственный запрос ОС вторник 09:00 и приглашение не записавшимся четверг 09:00;
- отсутствие напоминаний после окончательной обратной связи;
- перезапуск между подготовкой и публикацией;
- повторный и одновременный запуск;
- ручное изменение и приостановка черновика;
- частичная и массовая ошибка Telegram-доставки;
- задержанный запуск Actions и безопасная повторная обработка;
- исчерпание ресурса или имитация отказа записи с корректным сообщением владельцу;
- миграция с сохранением профиля, истории, обратной связи и ачивок;
- проверка основных экранов на мобильной и десктопной ширине, включая загрузки, пустые состояния и ошибки.

В репозитории должны быть инструкции для запуска, deploy, миграций, проверки фоновых процессов, ручного восстановления, корректировки черновика и настройки получателя служебных уведомлений. Выбранные пороги алертов и ограничения наблюдаемости указываются явно.

Готовность: недельные циклы проходят автономно, владелец получает предварительный состав и только важные сообщения о сбоях, новые релизы сохраняют пользовательские данные.

### Уточнение владельца: контроль Render

По решению владельца независимый монитор отказов Render и Telegram-уведомления о падении Render исключены из MVP. Доступность и деплои контролируются вручную в Render. Это уточнение отменяет требование внешнего триггера и независимого состояния доставки для общего отказа хостинга выше. Контроль этапов недельного цикла, служебный отчёт и уведомления об ошибках подготовки/публикации сохраняются. Интерфейс размещается на Pages, Render обслуживает только backend API.

## Уточнение интерфейса от 25 октября 2026

- Серверный gate: авторизация → все 3 шага онбординга → обязательный профиль → остальное приложение. Ни скрытие ссылок без защиты маршрутов, ни POST action=skip не обходят этапы. Навигация появляется только после сохранения профиля.
- Новый full_name (до 250 символов) — единое поле имени. first_name/last_name остаются для сохранности старых данных и Telegram; display_name использует full_name либо старое сочетание. Новые снимки фиксируют full_name, старые снимки не переписываются. Однословное имя допускается.
- Профиль первого заполнения не показывает достижения и выход; в заполненном профиле доступны редактирование трёх полей, достижения и выход. Статуса Telegram в профиле нет.
- Текущая неделя вычисляется по границе среды 09:00 МСК, а не по наличию у пользователя встречи. Следующая — строго следующий недельный период. Основной блок содержит текущую активность целиком, боковой — только запись на следующую.
- Outcome формы только yes/no. Yes требует rating 1–5; no требует comment и сохраняет rating=NULL. Клиентское раскрытие полей дополнено серверной валидацией и CHECK ограничения рейтинга в БД. Старые impression/again/pending остаются в данных, без выдуманных звёзд.
- История состоит из опубликованных Member, а не всех календарных недель. У каждого неокончательного ответа доступна оценка, у окончательного — результат без кнопки. Первое заполнение не ограничено давностью; изменение окончательного ответа остаётся доступным до ends_at+7 дней.
- Миграция 0006 только добавляет full_name с DB default='' и nullable rating, ограничение 1–5. Не обнуляет историю, ответы, имена или ачивки; старые INSERT совместимы. Аналитическое событие результата включает rating.

## Актуальный старт и статическая оболочка

Pages отдаёт весь HTML интерфейса; данные загружаются JSON API. Незалогиненное открытие и logout показывают первый шаг публичного онбординга; Telegram-код запрашивается только явным действием после трёх шагов. Главное авторизованное состояние — активности с немедленным каркасом/лоадером. История и профиль — панели поверх главного экрана с закрытием, лоадером и повтором ошибки. Вместо трёх текстовых вкладок — две иконки. Авторизация и обязательный профиль проверяются API с JSON 401/409 без HTML-редиректов. Logout отзывает сессию с JSON 200, повторный/истёкший ключ идемпотентен; UI не ждёт сети для возврата к введению. Ни поздний fetch, ни переход назад не восстанавливает отозванный вход.
