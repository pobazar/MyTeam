# Эксплуатация

## База и миграции

Данные приложения находятся в отдельной схеме `myteam` Supabase PostgreSQL. Не добавлять её в exposed schemas PostgREST. Отдельная роль `myteam_app` владеет только этой схемой, без SUPERUSER/CREATEDB/CREATEROLE/BYPASSRLS. `search_path=myteam,public` задан роли. Прямой URL с паролем хранится только в защищённом окружении Render, `sslmode=require`. Серверный ключ Supabase не нужен браузеру и не заменяет проверку прав приложением. MVP пока не загружает файлы: Storage не содержит пользовательских объектов приложения, публичные buckets не создаются.

`python manage.py migrate --noinput` создаёт пустую БД и применяет только новые версии. Не использовать flush, reset, DROP SCHEMA или пересоздание БД при деплое. Совместимые миграции: сначала nullable/новое поле, затем backfill отдельным шагом, затем ограничение после проверки старых строк. Откат приложения предпочтительнее обратной разрушительной миграции.

Перед разрушительной миграцией: остановить запись/worker, сделать `pg_dump --format=custom --schema=myteam` в защищённое хранилище, записать версию миграций; восстановить dump в отдельную БД и проверить профили, участие, снимки, feedback, ачивки. Только после успешной проверки выполнять изменение. Не выводить URL/пароль в командной строке или логи, использовать PG* окружение/защищённый service file. Восстановление: новая БД → pg_restore → проверки → переключение DATABASE_URL; оригинал не удалять. Если появятся Storage-файлы, отдельно копировать объекты и метаданные; SQL dump не сохраняет содержимое объектов. Тарифные backup/PITR не предполагаются доступными без проверки.

## Процессы и расписание

Web: `gunicorn config.wsgi:application --bind 0.0.0.0:$PORT --workers 2 --timeout 60` после `migrate --noinput`. Render health-check `/health/live`, БД проверяется `/health/ready`. `APP_ENV=production` проверяет обязательные серверные переменные при запуске; секрет сессий минимум 50 символов. Render `TG_BOT_TOKEN` переиспользуется, не переименовывается и не копируется в клиент. Supabase management API key используется только для управления ресурсами, не для запросов пользователей. Доступ приложению даёт отдельный `DATABASE_URL` с ролью `myteam_app`.

Отдельный Render Cron Job: `python manage.py tick` каждую минуту (`* * * * *`, расписание cron UTC). Логика внутри переводит сроки в Europe/Moscow: вторник 21:00 закрытие, 22:00 подготовка/отчёт, среда 09:00 публикация, понедельник 12:00 запрос, вторник 21:00 последний запрос. `FEEDBACK_HOUR`/`FEEDBACK_MINUTE` меняют только понедельничное время. Часы нельзя менять через пользовательский API. Render Cron — платный ресурс; создание только после разрешения владельца. На free web возможен холодный старт, но cron подключается к БД напрямую и не зависит от сайта.

Tick сериализуется строкой RuntimeLock в PostgreSQL. Каждый этап и его сообщения фиксируются одной транзакцией; ошибки этапа откатывают изменения, ошибка/инцидент сохраняются отдельно. Повтор `python manage.py tick` безопасен. Публикация после простоя более 6 часов не догоняется автоматически: раунд помечается expired с инцидентом; устаревшие приглашения не отправляются. После публикации никогда не пересоздавать распределение. SEND_TELEGRAM=false по умолчанию: плановые сообщения только записываются в очередь. Ответ на добровольный вход (/start) и запрос контактов отправляется сразу через ту же очередь; это не тестовая рассылка. Тесты используют отдельную БД и поддельный transport, никогда рабочие chat ID.

Очередь: `python manage.py deliver` обрабатывает до 20 сообщений; tick также запускает доставку. До 8 попыток при временной ошибке, backoff до 1 часа, Retry-After учитывается. Telegram 403 — постоянная ошибка и заблокированный канал. Успешные сообщения повторно не отправляются. Если процесс умер/ответ Telegram потерян после принятия запроса, статус unknown требует ручной проверки; автоматического повтора нет. После проверки оператор может изменить статус на pending, осознавая риск дубля. Абсолютная exactly-once доставка Telegram невозможна. Истёкшие приглашения/запросы и окончательно ответившие исключаются перед отправкой. Понедельничный запрос истекает при наступлении вторничного; нет двух догоняющих напоминаний одновременно.

## Telegram и получатель

Вход: /login выдаёт одноразовый случайный deep link, привязанный к браузерной сессии на 10 минут. Бот получает `/start l_<nonce>` в private-чате через webhook с `TELEGRAM_WEBHOOK_SECRET`. Произвольные поля веб-формы не удостоверяют личность. Идентичность — числовой Telegram ID. Возможность доставки отмечается отдельно, только после подтверждённой отправки сообщения bot_connected; изменение username не создаёт новый профиль.

Webhook задаётся Bot API setWebhook с URL `PUBLIC_URL/telegram/webhook/`, secret_token из серверного окружения, allowed_updates=[message], без drop_pending_updates. Не логировать URL Bot API — в нём токен. До переключения читать getWebhookInfo и не перехватывать чужой webhook. Полное имя бота — МАЙТИМ. getMe проверяет действительность токена, но не доставку владельцу.

Для включения служебных уведомлений @artemiy_mikhaylov должен активировать бота через вход приложения. Проверить числовые user ID и chat ID по доверенному private webhook, сверить профиль через getChat; затем сохранить OWNER_TELEGRAM_ID и OWNER_CHAT_ID только на сервере. До этого служебные сообщения не адресуются никому. Никогда не назначать владельца по имени из пользовательской формы. Провести одно согласованное служебное сообщение только проверенному получателю и проверить подтверждение Bot API; не использовать участников как тестовые адреса.

Контакты без username: кнопка в карточке открывает `/start m_<meeting UUID>`; бот проверяет опубликованное членство и отвечает inline-ссылками `tg://user?id=...`. Такие упоминания поддерживаются Telegram для пользователей, ранее написавших боту (условие входа). Закрытые встречи/чужие ID не раскрываются. Проверка ссылки на двух реальных согласованных аккаунтах без username — отдельный пункт интеграционной приёмки; модульные тесты проверяют только формирование и права. Нет внутреннего чата или хранения переписки.

## Ручная правка и пауза

Работать в транзакции и с блокировкой того же раунда, что использует планировщик:

```sql
begin;
set local search_path = myteam, public;
select id,state,starts_at,publication_paused from myteam_round where id = '<round UUID>' for update;
update myteam_round set publication_paused = true where id = '<round UUID>' and published_at is null;
select m.id,m.meeting_id,m.person_id,m.snapshot from myteam_member m where round_id = '<round UUID>';
-- Менять meeting_id только на встречу этого же раунда; снимки команды/города редактировать осознанно.
-- Встречи должны полностью покрыть active enrollments ровно по одному разу: пары и одна тройка при нечётном числе.
commit;
```

До снятия паузы выполнить серверную проверку `validate_draft(Round.objects.get(pk=...))` через manage.py shell. Затем в транзакции с FOR UPDATE снять publication_paused, повторить tick до конца шестичасового окна. prepared_at не очищать: повтор prepare не перезаписывает правки. Неверный состав блокирует публикацию. После публикации состав автоматически не меняется, отказ участника не перераспределяет группу. Сообщения владельца не являются командами подтверждения.

## Контроль

`python manage.py monitor` можно запускать отдельно от tick, но общий отказ Render/БД контролируется независимым GitHub Actions workflow. Для него нужны только repository secrets MYTEAM_OPS_SECRET и MYTEAM_TG_BOT_TOKEN. Числовой ID проверенного владельца, URL Pages и API заданы в scripts/external_monitor.py; workflow включён в коде. Проверяются и Pages, и закрытое состояние API. Состояние дедупликации хранится в Actions artifact (90 дней), не в БД приложения. Ошибка чтения состояния завершает проверку ошибкой, не сбрасывает дедупликацию. Если сама Actions-платформа недоступна или расписание задержано, точного SLA и немедленного Telegram-алерта нет; следить за неуспешными workflow. Самосообщение упавшего процесса не является единственным контролем.

Порог heartbeat/просрочки этапа — 10 минут. Очередь просрочена на 15 минут — инцидент. Массовая доставка: минимум 3 ошибки и доля неуспеха ≥50% за час, исключая единичные 403. Повтор алерта не чаще 24 часов, одно сообщение о восстановлении. Обычные операции не отправляют служебный спам. Логи показывают класс исключения/статус, не URL с токеном, тела запросов, комментарии или сырые исключения БД.

pg_database_size доступен PostgreSQL; DB_WARNING_BYTES задаётся оператором по фактически подтверждённому тарифу (0 выключает предупреждение, не проверку отказов). Остаток квот провайдера не предполагается доступным через API. Storage MVP не использует: нет файлового сценария, поэтому искусственный тест bucket не создаётся. Независимый health-check читает список buckets через серверный SUPABASE_SERVICE_ROLE_KEY и SUPABASE_URL; management key sbp_ для Storage не подходит. Этот read-only probe проверяет доступность API, а не загрузку объектов. Если файлы будут добавлены, включить отдельную пробу чтения/записи и проверку квоты; пока готовность файловых операций не заявляется.

Сопоставление команд: транслитерация, пунктуация, регистр, общая лексика русских/английских слов и однозначная аббревиатура существующего полного имени. Это не LLM и не полноценный перевод произвольных названий: сомнения остаются отдельными/неопределёнными группами. Полный подбор пар минимизирует лексикографический штраф; для нечётных когорт до 21 человека тройка перебирается полностью, выше — 128 случайных кандидатов и точный подбор остальных пар. Глобальная оптимальность тройки для больших когорт не гарантируется. Город не влияет на подбор, но определяет рекомендацию формата встречи.

## Релиз Pages и экономный cron

Pages уже настроен на main, корень репозитория. `.nojekyll` отключает обработку Django-шаблонов как Liquid. Индекс и JS статические; frontend API задан публичным origin Render. `FRONTEND_URL=https://pobazar.github.io/MyTeam` задаёт ссылки в уведомлениях вида /#/meetings/..., PUBLIC_URL остаётся адресом Render для webhook. Telegram webhook должен принимать message и callback_query.

Один Render cron `myteam-cycle`, минимальный Starter, `*/5 * * * *` UTC: `python manage.py tick --delivery-limit 100 && python manage.py monitor`. Действия недельного цикла выполняются только по своим сохранённым срокам МСК; остальные короткие запуски нужны для очереди, повторов и восстановления. Это один оплачиваемый cron-сервис, не пять сервисов. По официальной документации Render — минимум $1/месяц за cron и посекундная оплата реально отработанного времени; это нижняя граница, не обещание фиксированного счёта. Бизнес-расписание прежнее: понедельник 12:00, вторник 21:00/22:00, среда 09:00 МСК.

После согласия владельца платный cron разрешён. Служебный получатель проверен getChat и private-доставкой: OWNER_TELEGRAM_ID=776767993, OWNER_CHAT_ID=776767993, @artemiy_mikhaylov. Эти значения задаются сервером; права нельзя назначить через профиль.

GitHub Actions repository Secrets: MYTEAM_OPS_SECRET ← Render myteam-web OPS_SECRET; MYTEAM_TG_BOT_TOKEN ← TG_BOT_TOKEN. Другие Secrets и Variables не нужны. OPS_SECRET — серверный ключ доступа только к /health/operations, созданный при настройке; это не ключ Render или Supabase. Токен Telegram нужен независимому runner для уведомления владельца при отказе Render. Pages этих секретов не получает. Текущая GitHub-интеграция не имеет права записывать Secrets/Variables; владелец добавляет их через настройки, затем workflow_dispatch позволяет проверить watchdog.
