# Архитектура

Один модульный Django-сервис: JSON API проверяет права и состояние операций, ORM даёт транзакции и версионируемые миграции; HTML-оболочка находится в Pages. PostgreSQL — источник истины. SQLite предназначена только для локальной разработки. Ни микросервисов, ни универсального конструктора форматов.

Границы: users — идентичность/профиль; rounds — запись и сроки; activities — правила формата и инструкции; matching — распределение; notifications — outbox и доставка; jobs — устойчивые этапы; feedback — ответы и ачивки; monitoring — инциденты; analytics — история событий. Модели общие в models.py для явных ограничений и связей.

Activity имеет стабильный key, version, title, инструкции, build_groups, valid_distribution, фабрику feedback_form, шаблон карточки и achievement_key; конкретный подбор находится в activities/coffee.py. Снимок правил и профиля фиксируется на момент подготовки. Новый формат регистрируется в activities, использует общие профили/раунды/outbox, добавляет собственные правила и миграции, не меняя старую историю.

Системные часы передаются через Clock; FrozenClock используется только в изолированных тестах и никогда не принимает время из публичного запроса. Планировщик запускается внешним cron; таймер веб-процесса не используется.

Актуальное расписание владельца: ОС вторник 09:00; закрытие и подготовка вторник 21:00; публикация среда 09:00; приглашение не записавшимся четверг 09:00. Никакого автопродления записи.

Все чтения правил исторического раунда используют (activity, rules_version). VERSIONS сохраняет старые реализации; новую семантику вводить новой версией класса, не переписывая старую. Неизвестная версия блокирует обработку, а не подменяется текущими правилами. Feedback и условия ачивки делегируются формату; отдельный тест с группой из четырёх человек проверяет повторное использование общего цикла другим форматом без кофе-ограничений.

Pages — тонкий статический клиент без iframe и сборщика; существующие формы/представления остаются едиными на Django. /bridge/bootstrap создаёт анонимную серверную сессию для разрешённого Origin. Authorization переносит только случайный session key (не Telegram/Supabase/Render ключи); ротация при входе возвращается отдельным CORS-exposed заголовком. CSRF_USE_SESSIONS устраняет зависимость от cross-site cookies; состояние хранится в БД. CORS не использует wildcard, ответы сессий не кешируются. Планировщик использует отдельный заголовок X-Myteam-Scheduler-Token с GitHub OIDC JWT, не пользовательскую сессию.

Вход имеет отдельные стадии: одноразовый browser nonce + показанный код → запрос из private Telegram-чата → inline callback того же числового Telegram ID → confirmed_at → атомарное потребление браузером и смена session key/CSRF. Polling не авторизует неподтверждённую попытку. Callback подтверждает также реальную доступность private-чата. Миграции 0003/0004 добавляют поля без удаления данных; DB defaults сохраняют совместимость INSERT старой версии.

GitHub Actions schedule.yml вызывает POST /internal/schedule/. Подпись GitHub OIDC проверяется по публичному JWKS (RS256), issuer, audience, срокам, числовому repository_id и точному workflow_ref на main; допускаются только schedule/workflow_dispatch. Shared secret и перенос TG/DB ключей в GitHub не нужны. verify выполняет только проверку аутентификации и БД, run обрабатывает этапы и короткую пачку очереди. Runner повторяет запросы и временные ошибки до 70 минут в рамках одного запуска, каждый раз получая свежую identity; повторный tick сохраняет черновики и не дублирует сообщения. Часы из HTTP-запросов не принимаются.

Обязательные пользовательские этапы проверяются login_required до вызова представления, а навигация использует тот же признак готовности. ProfileForm предлагает full_name/team/city, не разделяя составное имя. Исторические раздельные имена и снимки сохраняются; display_name и снимок full_name дают совместимость без потери данных. Generic feedback использует radio yes/no и 1–5, отдельный общий interactions.js связывает условные поля как в Pages, так и в Django; серверная проверка остаётся обязательной. Member/Feedback, а не факт наличия Round, определяют участие и состояние истории. Старые текстовые ответы остаются окончательными по прежним данным без конвертации в рейтинг.

Актуальный клиент Pages владеет всей статической оболочкой в index.html и web/app.js/app.css. DOM клонируется из локальных template, данные JSON вставляются textContent/value, серверный HTML не парсится. Данные выдаются /api/*; read_models общие с legacy HTML представлениями. Native dialog сохраняет активности под историей/профилем; загрузка/ошибка имеют отдельные состояния. AbortController и версии авторизации/панелей предотвращают позднюю отрисовку и восстановление токена после logout. Публичный онбординг — локальное состояние до входа, он начинается заново при каждом гостевом открытии. Cookie-сессии/CSRF/Telegram подтверждение остаются серверными; logout локально мгновенный, отзыв серверной сессии — фоновый POST без редиректа. API описан в api.md. Legacy HTML оставлен лишь совместимости старых вкладок.
