# Архитектура

Один модульный Django-сервис: серверный рендеринг уменьшает клиентскую поверхность секретов, ORM даёт транзакции и версионируемые миграции. PostgreSQL — источник истины. SQLite предназначена только для локальной разработки. Ни микросервисов, ни универсального конструктора форматов.

Границы: users — идентичность/профиль; rounds — запись и сроки; activities — правила формата и инструкции; matching — распределение; notifications — outbox и доставка; jobs — устойчивые этапы; feedback — ответы и ачивки; monitoring — инциденты; analytics — история событий. Модели общие в models.py для явных ограничений и связей.

Activity имеет стабильный key, version, title, инструкции, build_groups, valid_distribution, фабрику feedback_form, шаблон карточки и achievement_key; конкретный подбор находится в activities/coffee.py. Снимок правил и профиля фиксируется на момент подготовки. Новый формат регистрируется в activities, использует общие профили/раунды/outbox, добавляет собственные правила и миграции, не меняя старую историю.

Системные часы передаются через Clock; FrozenClock используется только в изолированных тестах и никогда не принимает время из публичного запроса. Планировщик запускается внешним cron; таймер веб-процесса не используется.

При конфликте старого продукта и технического документа последнее напоминание — вторник 21:00 МСК, по явному указанию владельца и #16. Никакого автопродления записи.

Все чтения правил исторического раунда используют (activity, rules_version). VERSIONS сохраняет старые реализации; новую семантику вводить новой версией класса, не переписывая старую. Неизвестная версия блокирует обработку, а не подменяется текущими правилами. Feedback и условия ачивки делегируются формату; отдельный тест с группой из четырёх человек проверяет повторное использование общего цикла другим форматом без кофе-ограничений.

Pages — тонкий статический клиент без iframe и сборщика; существующие формы/представления остаются едиными на Django. /bridge/bootstrap создаёт анонимную серверную сессию для разрешённого Origin. Authorization переносит только случайный session key (не Telegram/Supabase/Render ключи); ротация при входе возвращается отдельным CORS-exposed заголовком. CSRF_USE_SESSIONS устраняет зависимость от cross-site cookies; состояние хранится в БД. CORS не использует wildcard, ответы сессий не кешируются. Операторский bearer health-token не смешивается с пользовательскими сессиями.

Вход имеет отдельные стадии: одноразовый browser nonce + показанный код → запрос из private Telegram-чата → inline callback того же числового Telegram ID → confirmed_at → атомарное потребление браузером и смена session key/CSRF. Polling не авторизует неподтверждённую попытку. Callback подтверждает также реальную доступность private-чата. Миграции 0003/0004 добавляют поля без удаления данных; DB defaults сохраняют совместимость INSERT старой версии.
