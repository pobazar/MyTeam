# Приёмка MVP

Дата: 24 октября 2026. Изолированные проверки не отправляют сообщения рабочим пользователям.

Проверено на локальном PostgreSQL 16: 35 тестов проходят, включая два последовательных раунда, границы вторника/среды, отсутствие автопродления, перезапуск и одновременные запуски scheduler/worker, повреждённый/приостановленный черновик, история снимков, индивидуальные ответы, ачивки и аналитические ревизии. Миграция 0001 → 0002 проверена на профиле, опубликованной истории, feedback и ачивке; повтор migrate сохраняет данные. SQLite: 33 пройдено, 2 проверки PostgreSQL-блокировок пропущены намеренно.

Отдельный pg_dump/pg_restore проверен в двух изолированных локальных PostgreSQL-базах: сохранены 2 профиля, 4 записи истории встреч, 1 ответ и 1 ачивка. UUID и контрольные суммы снимков/комментариев совпадают с оригиналом. Production БД этим прогоном не изменялась.

Браузер Chromium: 375px и 1280px, вход, активности, профиль, история, карточка, feedback без горизонтального скролла. Имитация обрыва POST сохраняет ввод, повтор успешно сохраняет форму. Нет debug/тестовых данных в рабочем интерфейсе; тестовые данные браузера находятся только в локальной SQLite.

Render API: подтверждён проект MyTeam. Старый пустой web-service использует Go runtime; новая реализация — Python. Supabase API: подтверждён ACTIVE_HEALTHY проект MyTeam, исходно прикладных таблиц не было; создана отдельная закрытая схема и ограниченная роль. Токен Telegram getMe действителен, бот @myteam_official_bot; webhook настроен на /telegram/webhook/ с секретом и подтверждён getWebhookInfo, имя бота исправлено на МАЙТИМ. Добровольной активации владельца пока нет.

Фактически проверены deploy https://myteam-web.onrender.com, главная страница и /health/live + /health/ready (200), применение миграций и подключение production PostgreSQL. Supabase REST не экспонирует схему myteam (только public,graphql_public). Storage list buckets возвращает 200, buckets отсутствуют; загрузка объектов не проверялась. В Render SUPABASE_API_KEY оказался management key, поэтому для read-only Storage probe получен отдельный проектный service_role, секрет остаётся только на сервере.

Не подтверждены: cron, доставка реальному владельцу после активации, контакты двух реальных пользователей без username. Создание платного Render Cron требует разрешения. Служебный получатель по числовому ID ещё не привязан; плановые сообщения выключены; добровольный /start и запрос контактов получают отдельный ответ. Независимый Actions-monitor подготовлен, но не включён: GitHub API возвращает 403 Resource not accessible by integration при записи repository Secrets/Variables. Нужны права администратора репозитория и проверенный получатель. /health/operations достоверно возвращает 503 scheduler_stale, поскольку cron ещё не создан.

Не считать пункты интеграционной приёмки выполненными на основании моков или одного HTTP 200 от management API. CI сначала выполняет collectstatic, затем тесты: первоначальный запуск выявил отсутствие manifest в чистом runner, порядок сборки исправлен.

Наблюдение тарифа: один из free Render rollout занял около 8 минут, во время переключения наблюдались HTTP-таймауты. Постоянная доступность web на free не гарантируется; отдельный cron должен обращаться к БД напрямую и не зависеть от web-процесса.

## Релиз Pages и нового входа

Новая проверка: 40 тестов на PostgreSQL, включая browser-bound подтверждение callback, запрет входа после одного /start, ротацию сессии, CORS/CSRF и работу без cookies между origins. Переход с 0001 на 0004 сохраняет профиль, историю, feedback и ачивку; DB defaults поддерживают INSERT старого приложения. Локальный Chromium 375/1280: код → ожидание (до подтверждения входа нет) → подтверждение → автоматический переход → онбординг/профиль, сохранение ввода при сбое сети, выход. Все данные изолированы в отдельной SQLite; реальных Telegram-получателей тест не использует.

Владелец фактически активировал бота: Telegram getChat подтвердил @artemiy_mikhaylov и числовой private chat ID. Платный минимальный Starter cron согласован; итог запуска и Pages фиксируются после проверки внешних ресурсов. Контакт без username отложен владельцем. Для внешнего watchdog владелец добавляет GitHub Secrets/Variables вручную; до включения флага он не считается активным.
