# Задержки API — 25 октября 2026

Причины: исходный API в Render Ohio, БД Supabase в Paris (eu-west-3); последовательные SQL-запросы проходили через Атлантику. Дополнительно middleware делал exists(session_key), затем Django ещё раз загружал ту же сессию. Сохранение неизменённой команды повторно читало команды и открывало отдельную транзакцию.

Исправления:
- бесплатный Render Frankfurt, тот же Supabase и SECRET_KEY сессий;
- 1 загрузка сессии вместо exists + load, без ослабления проверки истечения;
- 3 SQL на повторный GET профиля/истории;
- 4 SQL на сохранение имени/города с той же командой: сессия, пользователь, UPDATE, достижения;
- пересчёт команды и транзакция только если команда изменилась/ещё не нормализована;
- соединения с БД живут до 600 секунд вместо 60;
- безопасный Server-Timing для диагностики, без записи SQL и параметров.

## Измерение на реальном API

HTTP-запросы к /health/ready: SELECT 1 и чтение существования профилей, без записей и имитации пользователей. Старый и новый сервисы измерялись с одного cloud-клиента параллельно. Это небольшая выборка, не нагрузочный тест и не замер браузера пользователя.

| Сервис | Регион | Три полных ответа, мс |
|---|---|---|
| Прежний API | Ohio | 961, 962, 652 |
| Новый API | Frankfurt | 312, 306, 227 |

У нового API суммарное SQL-время этих двух запросов: 20.8, 19.8, 21.4 мс. Полное время внутри приложения: 98.1, 89.2, 22.3 мс (первые соединения с БД дополнительно инициализировались). Разница между временем приложения и HTTP включает сеть/прокси/TLS; одинаковая задержка у каждого пользователя не гарантируется.

Операции реального пользователя и отправка Telegram не использовались для теста. Бюджеты SQL, сохранность авторизации/CSRF и истечение сессии проверены в изолированном PostgreSQL. Старый Ohio адрес временно доступен открытым вкладкам, чтобы переключение не оборвало работу; после обновления страницы клиент использует EU и прежнюю серверную сессию.

Free Render может засыпать после простоя. Регион и оптимизация SQL ускоряют прогретые запросы, но не устраняют первый холодный старт бесплатного сервиса. Фоновый keepalive и дополнительные периодические рассылки не добавлены.

Проверка переключения: Pages отдаёт новый API origin, getWebhookInfo — новый webhook, Actions verify 40189965409 — success. 64 теста PostgreSQL и браузерные проверки 390/1440 проходят. Прежний сервис переименован в myteam-backend-ohio-legacy и временно обслуживает старые вкладки; их пользователю достаточно обновить страницу.

## Повторная проверка: что именно запрашивается

Прежние 3 SQL профиля состояли из чтения django_session (с проверкой expires), myteam_person и myteam_achievement. Теперь признак единственной MVP-ачивки first_coffee вычисляется EXISTS в SELECT пользователя: 2 SQL всего, из них один — данные профиля. Сохранение имени/города с прежней командой — 3 SQL, включая UPDATE.

История: (1) django_session, (2) myteam_person для авторизации/обязательных этапов, (3) myteam_member JOIN myteam_round LEFT JOIN myteam_feedback. Данные списка — один SQL; ненужный JOIN myteam_meeting удалён. Сессия остаётся серверной и проверяется при каждом запросе.

Активности ранее делали 9 SQL при существующей встрече: сессия, пользователь, две недели отдельно, своя встреча/ответ, запись на текущую неделю, участники встречи, запись на следующую неделю, отсутствие пары. Теперь обе недели и флаги enrollment/unmatched запрашиваются одним SELECT с индексируемыми EXISTS: 5 SQL всего при активной встрече, меньше в пустых состояниях. Auth/истечение сессий/обязательные этапы не обходятся. Кеш пользовательских данных не добавлен.

Полный HTTP-запрос не равен времени SQL или Django. В повторном замере /health/live без БД показал app=0.4 ms при полном HTTP=266.6 ms с cloud-клиента. При двух запросах на одном соединении первый занял 524.9 ms (TLS 32.4 ms), второй — 180.9 ms без нового подключения. Это время вне обработчика приложения, включая путь клиента/прокси и ожидание до Django. По этим замерам нельзя определить причину конкретных 500–800 ms пользователя: для этого нужны домен фактического запроса и его Server-Timing, затем Network Timing. Без этого не заявляется, что всё время занимает БД или Render.

65 тестов PostgreSQL закрепляют бюджеты и состояния страниц. Запрос домена нужен также для проверки, что открытая вкладка использует EU, а не оставшийся legacy Ohio API.

Read-only EXPLAIN ANALYZE в текущем Supabase: запрос данных профиля с EXISTS ачивки — planning 0.694 ms, execution 0.186 ms; запрос истории — planning 1.487 ms, execution 0.183 ms (текущий список пустой). Значения не включают сеть и не являются замером всего HTTP-запроса. Поля пользователя и токены не возвращались/не выводились. Новый код c59852a задеплоен в EU, dep-dbeuup8ae00c73e76dvg — live. Бюджеты проверены изолированными тестами, включая появление новой ачивки без кеширования и лишнего SQL.
