Результат: PASS. Четыре вымышленных пользователя в отдельной SQLite, реальные Django и Pages-клиент на разных локальных origin. Chromium 1440×1000 и 390×844. Сессии имитируют уже завершённый Telegram-вход; реальные Telegram, Supabase и участники не используются. Все внешние запросы браузера блокировались: 0 попыток внешнего запроса, 0 ошибок JavaScript. Скриншоты — реальный DOM без дорисовки.

## Актуальный флоу: статический Pages + JSON API

Новый сценарий проверен в Chromium на 1440 и 390 px, с отдельной SQLite и имитацией подтверждения бота. Сайт гостя сразу показывает три статических шага; повторное открытие гостем снова начинается с первого шага. До явного третьего шага нет ни API-вызовов, ни кода Telegram.

После входа — обязательный профиль, затем главный экран с двумя неделями. Каркас, заголовок, иконки и экспериментальная подпись видны при искусственно удержанном запросе API. Профиль и история открываются native dialog поверх активностей, с крестиком и Escape. Проверены загрузка, 503 и повтор для всех трёх экранов; ошибка сохранения не теряет ввод. Закрытая панель не восстанавливается поздним ответом.

Logout проверен при искусственно удержанном серверном запросе: UI немедленно показывает введение, локальный токен удалён, код не создаётся. После разрешения запроса ответ 200 JSON, прежняя DB session отозвана. Перезагрузка остаётся на введении без API. Ни одного 401 при нормальном выходе, ни одного HTML-ответа/legacy HTML endpoint в сетевом трейсе.

Также пройдены запись, положительный результат с 4 звёздами, персональная ачивка, отрицательный результат из истории, возврат в историю и профиль. 74 теста PostgreSQL проходят, включая JSON/CSRF/приватность/ротацию и идемпотентный выход. Проверки и рассылки изолированы от production.

## Предыдущий прогон до перехода на JSON-клиент

1. Все четыре проходят три шага без пропуска и навигации. Затем сохраняют обязательные full_name/team/city; до сохранения нет вкладок и достижений.
2. Новый участник видит приветственное состояние текущей недели; давно зарегистрированный не записавшийся — состояние пропуска. Следующая неделя всегда отдельная.
3. Трое записываются, четвёртый пропускает. Изолированные часы: вторник 21:00 — закрытие и подготовка одной тройки; среда 09:00 — публикация. Активных записей на следующую неделю автоматически не создаётся.
4. В основной карточке опубликованы участники и инструкции. Компактная боковая карточка позволяет отдельно записаться на следующую неделю и отменить запись; в базе сохраняется неактивная запись отмены, без активного участия.
5. Анна выбирает «Да», ставит 4 звезды без комментария. Форма возвращает в активности; основной блок благодарит, повторного действия оценки нет. Ачивка выдана.
6. Михаил выбирает «Нет» и указывает причину. Звёзды скрыты и в БД rating=NULL. Ачивка за отказ не выдаётся.
7. В обычном профиле доступны все три поля, достижения и выход. Telegram-статуса нет.
8. После окончания раунда история Анны показывает 4 звезды, Михаила — «Не получилось провести активность». Кнопки оценки скрыты.
9. Елена не отвечала во время активности: из истории открывает общую форму и ставит 5 звёзд. Возврат в историю, кнопка исчезла. История пропустившего Дмитрия пустая.
10. Итог: 4 профиля, 3 ответа (4/5/NULL), 2 личные ачивки, 0 настоящих отправок, 0 автоматических записей. На мобильном нет горизонтального скролла.

## Дополнительные проверки

61 тест PostgreSQL: обязательные этапы и прямые URL, POST action=skip не пропускает онбординг, старые имена и ответы после миграций 0001→0006, совместимость старых INSERT, снимки профиля, границы рейтинга, обязательная причина отказа, первая оценка давней недели, скрытие повторной оценки, OIDC, расписание и конкурирующие воркеры. Историческим текстовым ответам не придумываются звёзды.

Это сценарный локальный прогон. Он не подтверждает реальную доставку Telegram и не заменяет первое срабатывание GitHub schedule. Расписание этим изменением не меняется.
